# Feature Specification — `accounts-access` (`metro-core`)

- **Feature folder:** `.ai/sdd/specs/accounts-access/`
- **Parent system spec:** `docs/spec/requirements.md` v2 (`FR-ACC-01`, `FR-ACC-02`, `FR-ACC-03`, `NFR-SEC-01`, `NFR-SEC-02`)
- **Related ADRs:** `docs/adr/ADR-003-canonical-roles-and-authorization.md`, `docs/adr/ADR-005-specifications-artifacts-vs-prompts.md`
- **Status:** Reviewed (PL6)

## 1. Scope and Boundaries

This feature governs account creation, authentication (JWT access + refresh tokens), role-based authorization (`Passenger` vs. `Staff`), and resource-ownership enforcement in `metro-core`.

- **In scope:** Self-registration of `Passenger` accounts (`FR-ACC-01`), JWT authentication and canonical role enforcement (`FR-ACC-02`), staff-only user management endpoints (`NFR-SEC-02`), password hashing (`NFR-SEC-01`), and self-profile retrieval (`/api/v1/users/me`, `FR-ACC-03` foundation).
- **Out of scope:** Social login / external IdP, staff self-registration (`docs/spec/requirements.md` §7), passenger tickets/subscriptions/notifications ownership (implemented inside the `tickets` and `subscriptions-notifications` feature specs).

## 2. Requirements (EARS + Origin)

| ID | Statement (EARS) | Source | Origin | Pri |
| --- | --- | --- | :---: | :---: |
| `FR-ACC-01` | The system shall let a visitor create a `Passenger` account with e-mail and password (optional profile fields `Name`, `Document`, `Phone`). If an account with the same e-mail already exists, then the system shall reject creation with HTTP `409 Conflict` and an English message. | SRC-07 | S | Must |
| `FR-ACC-02` | The system shall authenticate active users and assign each account exactly one canonical role: `Passenger` or `Staff`. When an unauthenticated caller or a `Passenger` creates an account, the system shall force the role to `Passenger`; only an authenticated `Staff` user may create or assign `Staff`. | SRC-07, SRC-08 | D + T (D-06, ADR-003) | Must |
| `FR-ACC-03` | While authenticated as `Passenger`, the system shall restrict account-scoped access to the caller's own identity (`/api/v1/users/me`) and own resources. | SRC-04, SRC-07 | D | Must |
| `NFR-SEC-01` | The system shall store passwords only as salted hashes generated by an adaptive algorithm (PBKDF2-SHA256) and enforce password complexity (≥8 chars, upper, lower, digit). | SRC-07 | D | Must |
| `NFR-SEC-02` | Every `Staff` endpoint (`GET/PUT/DELETE /api/v1/users*`) shall require the `Staff` role; anonymous calls shall return `401` and `Passenger` calls shall return `403`. | SRC-08 | D | Must |

## 3. Acceptance Scenarios (Given / When / Then)

```gherkin
Scenario: ACC-S1 — Visitor registers with email and password only (FR-ACC-01, FR-ACC-02)
  Given no account exists with email "passenger@example.com"
  When an unauthenticated visitor posts {"email":"passenger@example.com","password":"Secret123!"} to POST /api/v1/users
  Then the response is 201 Created with the new user ID
  And the persisted user has Role = "Passenger" and a salted password hash (never plaintext)

Scenario: ACC-S2 — Duplicate email registration is rejected in English (FR-ACC-01)
  Given an account already exists with email "passenger@example.com"
  When a caller submits POST /api/v1/users with email "passenger@example.com"
  Then the response is 409 Conflict with message "Email is already registered."
  And no second user row is inserted

Scenario: ACC-S3 — Legacy or non-canonical roles are rejected (FR-ACC-02, ADR-003)
  Given a create or update user request specifying role "master", "client", "admin", "user", or "STAFF"
  When command validation runs
  Then validation fails on field Role with message "Role must be Passenger or Staff."

Scenario: ACC-S4 — Self-registration cannot escalate privileges to Staff (FR-ACC-02, NFR-SEC-02)
  Given an unauthenticated visitor or authenticated Passenger sends POST /api/v1/users with role "Staff"
  When UserController.Create processes the request
  Then command.Role is overwritten to "Passenger" before dispatching to CreateUserHandler
```

## 4. Assumptions and Open Questions

- **Decision (ADR-003):** Legacy database roles (`master`, `client`) are migrated to `Staff` and `Passenger` via EF Core migration `20261124120000_CanonicalUserRoles` and guarded by PostgreSQL constraint `CK_User_Role`.
- **Open note:** `PasswordRecoveryController` and `Metro.Infrastructure.File` remain from the initial starter template; team must decide before Final Delivery whether to formalize password recovery as a derived requirement or remove unused file storage (`KISS`, `T05`).
